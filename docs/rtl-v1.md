# RTL v1: 전체 기능

`rtl/v1/`. v0(입법 모드만)에 빠져 있던 것을 모두 넣었어요. 기준 모델은 `sim/polis/hw1.py`예요.

| 파일 | 내용 |
|---|---|
| `polis_tile1.v` | 타일: 동기 SRAM, 누설·휴지·항상성(1, 6조), 학습부(2, 3, 7b조 + 공로), 보상 스윕(8조), 설정 읽기/쓰기 포트 |
| `polis_router.v` | 라우터 (v0과 같음) |
| `polis_mesh1.v` | 메시: 헌법 파라미터 배포, 틱 장벽, 보상 명령, 설정 읽기 선택, 출력 관찰 포트 |
| `polis_nep.v` | 관문 브리지: NEP v1 RUN 바이트 → 입력·틱 실행 → RESULT 바이트, 잘못된 요청에는 ERROR |
| `polis_soc1.v` | 메시 + 관문 브리지 |

## 설계 결정: 하드웨어와 펌웨어의 분담

| 매 틱 반복되는 일 → **하드웨어** | 드물게 구조를 바꾸는 일 → **관리 코어 펌웨어** |
|---|---|
| 발화, 누설, 휴지 (1조) | 노드 이주 |
| 항상성 (6조) | 새 연결 만들기 (4조) |
| 강화·망각·가지치기 (2, 3조) | 영향력 상한 정리 (5조) |
| 표적 억제 (7b조) | 사용 끝난 공간 정리 (미구현) |
| 공로 누적, 보상 스윕 (8조) | |

펌웨어는 구역마다 있는 작은 범용 코어가 틱 사이에 **설정 포트**로 표를 읽고 써서 수행해요.
메모리 할당처럼 드물고 복잡한 일을 고정 회로로 만들면 면적만 커지기 때문이에요.
`hw1.Firmware`가 펌웨어의 동작 모델이고, 모든 표 수정을 설정 포트 명령(복사/쓰기)으로 기록해요.
RTL 검증에서는 테스트벤치가 이 명령을 실제 설정 포트로 실행해요.

### 바뀐 헌법 조항

- **5조**: "보내는 쪽 영향력 상한" → **"받는 쪽 영향력 상한"**(시냅스 크기 조절).
  연결 표가 받는 타일에 있어서, 보내는 쪽 합을 구하려면 여러 타일의 값을 모아야 해요. 받는 쪽 합은 한 타일 안에서 끝나요.
- **8조 공로**: 실수 모델의 공분산 공로 대신, 3비트 동시 발화 횟수. 기대 보상을 뺀 값(delta)은 선생님(호스트)이 계산해서 보내요.
- **4조**: 함께 발화한 쌍 사이의 새 연결을 펌웨어가 만들어요. 데이터 경로에는 할당 회로가 없어요.

### 이주 방식

- 이주는 **틱 장벽 동안**, 네트워크가 비어 있을 때 일어나요.
- 보내는 쪽 팬아웃 목록은 **즉시 교정**해요. 그래서 이 구현에서는 전송 포인터가 필요 없어요.
  (지연 교정과 전송 포인터는 이주 지연을 줄이는 최적화로 남겨둬요.)
- 옮겨간 노드의 옛 칸은 **한 틱 동안 비워두고** 해제해요. 직전 틱에 발화했다면 그 스파이크를 옛 칸에서 내보내야 하거든요.
  처음 구현에서 이 부분을 빠뜨려 스파이크가 사라졌어요. RTL과 모델이 같은 펌웨어를 따랐기 때문에 RTL 대 모델 비교로는
  안 보였고, **"이주한 실행 = 이주 안 한 실행" 투명성 검사**로 잡았어요.

## 고정소수점 형식

| 항목 | 형식 |
|---|---|
| 시냅스 24b | 가중치 w12 (부호, 1/256) · 목적지 8b · 학습 허용 1b · 공로 3b. 전위에는 w12 >>> 4 (1/16)를 더함 |
| 노드 36b | 임계값 int16 · 휴지 4b · 전위 int16 (1/16) |
| 발화율 8b | 지수 평균, 256 = 매 틱 발화 |
| 색인 50b | v0과 같음 |

학습은 1/256 해상도로 하고, 누산은 1/16로 해요. 같은 24비트 안에서 v0의 남는 목적지 비트를 가중치 소수부로 썼어요.

### 1. 공동 시뮬레이션 (`tools/rtl1_build.py`)

60틱 동안 입력 8%, 10틱마다 보상, 10틱마다 새 연결 3개, 20틱마다 상한 정리, 15틱마다 노드 3개 이주.

- 매 틱 발화한 노드 집합

## 합성 (Yosys, 타일당 노드 256, 색인·시냅스·팬아웃 4096칸)

| 블록 | 게이트 트랜지스터 | 플립플롭 | 합계 (FF 24T) | 가장 긴 논리 경로 |
|---|---|---|---|---|
| 타일 v1 | 81,126 | 972 | 약 104,500 | **181단** |
| 라우터 | 35,572 | 425 | 약 45,800 | 33단 |
| 관문 브리지 | 6,552 | 138 | 약 9,900 | 26단 |

- 타일 + 라우터 로직: 약 15만 트랜지스터 → **0.0011–0.0023 mm²** (65–134 MTr/mm² 가정). v0의 약 1.5배.
- 타일 SRAM: 64 KiB. 방문 목록(8192칸)이 그중 17 KiB예요. 방문 목록을 1024칸으로 줄이면(넘치면 그 틱의 학습 일부 생략) 49 KiB.
  → 0.011–0.021 mm². **로직은 여전히 SRAM의 약 1/10.**

### 타이밍

공정 라이브러리가 없어서 절대 주파수는 못 구해요. 대신 플립플롭 사이 가장 긴 게이트 단수를 봤어요.
**타일의 181단은 라우터(33단)의 5배 이상이에요.** 노드 갱신이 한 사이클에
누설 곱셈(16×9) → 덧셈 → 잘라내기 → 임계값 비교 → 발화율 → 임계값 조정 → 범위 제한을 모두 해서 그래요.
라우터 수준의 클록을 쓰려면 갱신부를 5–6단 파이프라인으로 나눠야 해요. 노드는 서로 독립이라 파이프라인은 어렵지 않아요.

## 아직 없는 것

- 갱신부 파이프라인 분할 (위 타이밍)
- 가장 많이 쓰는 경로의 처리량: 갱신은 사이클당 노드 1개, 학습은 시냅스당 2사이클 (모델은 8레인 가정)
- 공간 정리(가비지 컬렉션): 이주·성장 후 남은 묘비 항목과 옛 세그먼트를 펌웨어가 모아 정리
- 지연 교정 + 전송 포인터 (이주 지연 최적화)
- 관리 코어 자체 (RISC-V 등)와 이더넷 MAC·TCP/IP 스택: 기존 IP를 쓸 부분이라 RTL에 넣지 않았어요
- 실제 공정 라이브러리로 합성, 배치·배선, 전력 분석
